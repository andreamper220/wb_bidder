# Инструкции для AI-агента

Контекст проекта, ограничения процесса и порядок работы. Детальные правила по областям —
в [`.cursor/rules/`](.cursor/rules/). Обоснование этой конструкции — в
[docs/02-AI-WORKFLOW.md](docs/02-AI-WORKFLOW.md).

## Что это за система

Биддер для рекламы Wildberries: раз в N минут читает статистику из WB API, сравнивает эффективность
с экономическими порогами селлера и корректирует ставки поисковых кластеров. Управление ставками без
ML-оптимизации.

**Главное свойство контекста:** система тратит деньги селлера без присмотра человека. Ошибка в коде
здесь не «баг в бэклоге», а расход, который нельзя вернуть. Поэтому осторожность приоритетна перед
скоростью, а явный отказ — перед догадкой.

## Стек и команды

Symfony 7.2, PHP 8.4, PostgreSQL 16, Redis (Messenger), EasyAdmin 5, Doctrine ORM 3.

```bash
docker compose run --rm app php bin/phpunit          # тесты
docker compose run --rm app php bin/console wb:demo-stand --reset   # демо на моках
bash scripts/gates.sh                                # локальные гейты (обязательно перед PR)
```

Разработка идёт с `WB_API_MOCK=1`. Команды, обращающиеся к боевому API, не запускать.

## Ограничения процесса

Эти три правила важнее остальных, потому что нарушение каждого делает проверку работы бессмысленной.

**1. Не менять код и его тест в одном шаге.** Если тест упал — либо чинить код, либо прийти с
обоснованием, что неверна спецификация. Правка ожидаемого значения в тесте стратегии или гарда для
«зелёного CI» недопустима: таблицы решений — это спецификация, и её меняет человек.

**2. Не расширять объём задачи.** Найденная попутно проблема идёт в отчёт, а не в диф. Изменения вне
перечисленных в задаче файлов — основание отклонить PR целиком, независимо от их качества.

**3. Не выводить факты о внешнем API по аналогии.** Новый эндпоинт, поле или единица измерения —
только со ссылкой на раздел документации. Если ссылки нет, надо сказать «не знаю, требуется проверка
по спецификации», а не достроить путь по образцу соседнего метода. Одна такая догадка уже есть в
кодовой базе: [KI-02](docs/KNOWN-ISSUES.md#ki-02).

## Definition of Done

- [ ] Диф не выходит за перечисленные в задаче файлы
- [ ] Каждая строка таблицы решений — отдельный тест-кейс с явными числами
- [ ] `scripts/gates.sh` проходит
- [ ] Новых зависимостей нет (или согласованы отдельно)
- [ ] Значения по умолчанию в `Campaign` не изменены
- [ ] Каждое утверждение о WB API имеет ссылку на спецификацию
- [ ] Документация соответствует поведению после изменения
- [ ] Найденные попутно проблемы — в отчёте, а не в дифе

## Что сообщать в отчёте

1. Что сделано и в каких файлах.
2. Где пришлось делать допущения — и какие именно.
3. Что осталось непроверенным и каким способом это следует проверить.
4. Найденные попутно проблемы (без исправления).

Пункт 3 — обязательный. «Готово, всё работает» без указания границ проверки считается неполным
отчётом: тесты на моках не проверяют запись в WB, и это надо называть прямо.
