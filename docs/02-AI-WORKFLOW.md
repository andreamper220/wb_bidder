# 2. Реализация через AI: что отдаю агенту, правила и гейты

## Исходное

AI-агент пишет код быстрее меня и делает это на уровне хорошего мидла. Ошибается он тоже как
хороший мидл — но с двумя отличиями, которые полностью определяют процесс:

1. **Он не сомневается.** Придуманный путь эндпоинта выглядит в дифе ровно так же уверенно, как
   выписанный из спецификации. Человек, который не знает API, обычно спросит; агент — допишет по
   аналогии. Пример из этого проекта: [KI-02](KNOWN-ISSUES.md#ki-02).
2. **Он оптимизирует наблюдаемый критерий, а не цель.** Если критерий — «тесты зелёные», он получит
   зелёные тесты. В биддере это особенно опасно: самый рискованный код (запись ставки в WB) в
   mock-режиме вообще не исполняется, поэтому «100% тестов прошло» ничего не говорит о деньгах
   ([KI-13](KNOWN-ISSUES.md#ki-13)).

Отсюда вся конструкция ниже: **разделяю работу не по сложности, а по цене ошибки и по её
обратимости**. Сложный, но проверяемый код — агенту. Простой, но необратимый — руками.

```
                     обратимо                     необратимо
              ┌───────────────────────┬───────────────────────────┐
  дешёво      │ агент, ревью по       │ агент пишет,              │
  проверить   │ диагонали             │ проверяю построчно        │
              │ (CRUD, DTO, шаблоны)  │ (миграции, конфиги)       │
              ├───────────────────────┼───────────────────────────┤
  дорого      │ агент по таблице      │ пишу и проверяю сам       │
  проверить   │ решений, которую      │ (единицы денег, контракты │
              │ пишу я                │ API, границы гардов)      │
              └───────────────────────┴───────────────────────────┘
```

## 1. Что делаю руками

Не потому что агент не справится, а потому что **ошибка здесь не проявится ни в тестах, ни в
ревью — только в деньгах**.

| Область | Почему руками |
|---|---|
| **Экономическая модель**: формулы `CPA₀`, `ROAS₀`, вывод порогов из маржинальности ([§3 ТЗ](01-TECHNICAL-SPEC.md#3-экономическая-модель)) | Агент напишет любую правдоподобную формулу, и она пройдёт все тесты. Неверный `target_cpa` — это не баг, это медленная потеря прибыли без единого симптома |
| **Числовые границы предохранителей**: min/max ставки, максимальный шаг, cooldown, порог паузы | Это решение о допустимом риске, а не о коде. Агент склонен ставить «красивые» значения (10%, 15%) и обосновывать их постфактум |
| **Контракты WB API**: пути, единицы измерения, лимиты | Единственный источник — спецификация. Модель может «помнить» устаревшую версию. Проверяю глазами и фиксирую снапшот схемы в репозитории |
| **Проектирование очередей и границ транзакций** | Ошибка даёт частично применённые изменения ставок — самый неприятный класс инцидентов |
| **Схема БД и миграции для прода** | Необратимо на живых данных |
| **Всё, что делает запись в WB** | Единственная операция, которая тратит чужие деньги. Ревью построчно, без исключений |
| **Решение о включении боевого режима** | Организационное решение, не техническое |
| **Секреты, доступы, права** | Агент не получает прод-креды. Никогда |
| **Таблицы решений для тестов стратегии** | Тест — это спецификация. Если её пишет тот же агент, что и код, проверка становится тавтологией (см. правило [R-11](#r-11)) |

## 2. Что отдаю агенту

| Область | Почему безопасно | Как проверяю |
|---|---|---|
| Бойлерплейт: сущности, репозитории, EasyAdmin CRUD, DI-обвязка | Ошибка видна сразу, чинится дёшево | Тесты + запуск |
| DTO, мапперы ответов API | Механическая работа с высокой плотностью деталей — агент тут лучше человека (не устаёт на 40-м поле) | Контрактный тест на зафиксированном примере ответа |
| Реализация стратегии **по готовой таблице решений** | Таблицу написал я; агент переводит её в код | Ровно те же тесты, что и таблица |
| Реализация предохранителей по описанию инварианта | Инвариант формулируется в одну строку и проверяется перебором | Property-тесты |
| Mock-провайдеры, фикстуры, демо-стенд | Не участвует в проде | Ревью по диагонали |
| Рефакторинг под заданный интерфейс, переименования, извлечение классов | Механическое преобразование, поведение фиксировано тестами | Зелёные тесты + чтение дифа |
| Инфраструктура: Dockerfile, compose, конфиги — **как черновик** | Быстрый старт | Проверяю каждую строку: здесь легко получить `WB_API_MOCK=0` в dev |
| Документация по существующему коду | Ускорение в разы | Сверяю утверждения с кодом. Здесь агент чаще всего врёт — описывает задуманное как сделанное ([KI-05](KNOWN-ISSUES.md#ki-05)) |
| Тесты **на уже согласованное** поведение (краевые случаи, которые я не перечислил) | Расширение покрытия | Проверяю, что тест проверяет поведение, а не повторяет реализацию |

## 3. Формат задачи для агента

Задача без инвариантов и без запретов — это приглашение к творчеству. Формат, который я использую:

````markdown
## Задача
Реализовать `DeadBandGuard` — предохранитель, запрещающий изменение ставки,
если относительное изменение меньше порога.

## Файлы
Создать:   src/Bidding/Guard/DeadBandGuard.php
Изменить:  config/services.yaml (добавить в цепочку ПОСЛЕ MinMaxBidGuard, ДО CooldownGuard)
Создать:   tests/Unit/Bidding/Guard/DeadBandGuardTest.php
НЕ ТРОГАТЬ: src/Bidding/Strategy/**, src/Entity/Campaign.php

## Инварианты
1. Реализует BidGuardInterface, возвращает ?string (код причины или null).
2. Возвращает 'below_dead_band', если |new − old| / old < min_change_pct / 100.
3. Для действий HOLD и PAUSE всегда возвращает null (не вмешивается).
4. old = 0 → возвращает null (нельзя делить на ноль, первая установка ставки разрешена).
5. Чистая функция: без обращений к БД, HTTP и текущему времени.

## Таблица решений (это и есть тест-кейсы)
| old   | new   | action | min_change_pct | ожидание         |
|-------|-------|--------|----------------|------------------|
| 10000 | 10200 | Up     | 3              | 'below_dead_band'|
| 10000 | 10400 | Up     | 3              | null             |
| 10000 |  9800 | Down   | 3              | 'below_dead_band'|
| 10000 |  9600 | Down   | 3              | null             |
| 10000 | 10000 | Hold   | 3              | null             |
|     0 |  5000 | Up     | 3              | null             |

## Definition of Done
- Все строки таблицы — отдельные тест-кейсы.
- `scripts/gates.sh` проходит.
- Диф не содержит изменений вне перечисленных файлов.

## Запрещено
- Менять значения по умолчанию в Campaign.
- Добавлять зависимости в composer.json.
- Менять порядок существующих гардов в цепочке.
````

Три обязательных элемента, которые я добавил после набитых шишек:

- **Список «НЕ ТРОГАТЬ»** — без него агент «попутно улучшает» соседний код, и диф на 40 строк
  превращается в диф на 400, который никто внимательно не прочитает.
- **Таблица решений с конкретными числами** — она же тест, она же спецификация, она же то, что я
  проверяю вместо чтения кода.
- **Запрет на новые зависимости** — иначе в `composer.json` появляется пакет «на будущее», который
  никогда не будет использован (именно так там оказался `symfony/rate-limiter`, см. [KI-05](KNOWN-ISSUES.md#ki-05)).

## 4. Правила проекта

Правила лежат в репозитории и подхватываются агентом автоматически ([`.cursor/rules/`](../.cursor/rules/),
[`AGENTS.md`](../AGENTS.md)). Каждое правило появилось из конкретной ошибки, а не из общих
представлений о хорошем коде — поэтому в таблице есть колонка «после какого случая».

### R-1 — Деньги

Файл: `.cursor/rules/10-money-and-units.mdc`

- Ставки — только целые `int` в **копейках**; суммы — строки/`DECIMAL`, арифметика через `App\Math\Bc`.
- `float` в денежном пути запрещён, включая промежуточные вычисления и `round()`.
- Имя переменной, поля и параметра обязано содержать единицу: `bidKopecks`, `spendRub`. `$bid` — не проходит ревью.
- При пересечении границы с внешним API единица указывается в docblock со ссылкой на документацию.

*Появилось после:* [KI-01](KNOWN-ISSUES.md#ki-01) — копейки, отправленные в поле, документированное как рубли.

### R-2 — Границы слоёв

Файл: `.cursor/rules/20-architecture-boundaries.mdc`

- `HttpClientInterface` разрешён только в `src/WbApi/`.
- `EntityManagerInterface` запрещён в стратегиях, гардах, слиянии и в `src/Metrics/` — они работают
  со значениями. Исключение — `src/Bidding/Pipeline/`, чья задача как раз записать решение.
- `new \DateTimeImmutable()` внутри стратегий и гардов запрещён: время передаётся аргументом.
- Стратегии и гарды не имеют состояния и побочных эффектов.

*Зачем:* именно эта чистота делает возможными property-тесты. Как только в гард попадает БД, гейт G4
превращается в интеграционный тест, который никто не станет прогонять на каждом коммите.

### R-3 — Внешний API

Файл: `.cursor/rules/30-wb-api.mdc`

- Новый эндпоинт или новое поле — **только со ссылкой на официальную спецификацию в описании PR**.
  Формулировки «обычно у WB это так», «по аналогии с v1» — основание для отклонения без обсуждения.
- Лимиты частоты живут в конфиге, не в коде.
- Ответ API разбирается через маппер в DTO; массивы из `toArray()` не ходят по домену.
- Любой не-2xx — типизированное исключение, а не `RuntimeException` с текстом.

*Появилось после:* [KI-02](KNOWN-ISSUES.md#ki-02) — путь `/adv/v1/normquery/stats`, которого нет в документации.

### R-4 — Изменение поведения ставок

Файл: `.cursor/rules/40-bidding-domain.mdc`

- Изменение стратегии, гарда или значения по умолчанию — **отдельный PR**, не «попутно».
- В PR обязательны: обновлённая таблица решений, запись в журнале изменений стратегии, оценка влияния
  («какая доля кластеров изменит решение»).
- Значения по умолчанию в `Campaign` менять запрещено без явного указания в задаче: они уже стоят
  в БД у существующих кампаний, и «улучшение дефолта» тихо меняет поведение боевых кампаний.
- Добавлять новые действия в `BidAction` запрещено без обновления таблицы слияния и всех гардов.

### R-5 — Безопасность по умолчанию

Файл: `.cursor/rules/50-safety.mdc`

- Любое новое действие, влияющее на расход, обязано проходить цепочку гардов. Обход цепочки —
  отклонение.
- Новый код, пишущий в WB, обязан уважать `dry_run` и kill switch.
- При неопределённости (нет данных, устарели, ошибка API) действие по умолчанию — `HOLD`, и `HOLD`
  обязан быть явным, а не результатом того, что «ничего не сработало».
- `DOWN` и `PAUSE` не блокируются новыми гардами без отдельного согласования.

### R-6 — Тесты

Файл: `.cursor/rules/60-tests.mdc`

- Никаких сетевых вызовов в тестах; только `MockHttpClient` и фикстуры из `tests/Fixtures/`.
- Каждая ветвь стратегии и каждый код причины — отдельный тест-кейс с явными числами. Циклы по
  массиву кейсов внутри одного теста запрещены: падение должно указывать на строку таблицы.
- Тест не должен повторять формулу реализации. `assertSame($old * 1.1, $calc->...)` — это не тест.
- Для кода, который пишет во внешний API, обязателен контрактный тест на тело запроса.

### R-7 — Секреты и окружение

- Реальные токены в репозиторий не попадают ни в каком виде, включая примеры и тесты.
- `WB_API_MOCK=1` — значение по умолчанию везде, кроме явного прод-конфига. Небезопасное значение
  требует осознанного действия человека.
- Агент не запускает команды, обращающиеся к боевому API.

### R-8 — Стиль

- `declare(strict_types=1)`, `final` по умолчанию, `readonly` для DTO, enum вместо строковых констант.
- Публичные методы типизированы полностью, включая generics в аннотациях коллекций.

### R-9 — Диф

- Один PR — одна задача. Форматирование не смешивается с логикой.
- Комментарий в коде допустим только там, где он объясняет **ограничение**, а не пересказывает
  строку ниже.
- Мёртвый код, «задел на будущее» и пустые директории не проходят ревью.

### R-10 — Документация

- Документация описывает **реализованное** состояние. Планы — в отдельном разделе, помеченном как план.
- Изменение поведения → изменение документации в том же PR.

*Появилось после:* [KI-05](KNOWN-ISSUES.md#ki-05) — `QUEUES.md` описывал rate limiting, которого нет в коде.

### R-11

**Агент не имеет права одновременно менять код и тест, который этот код проверяет.**

Самое важное правило из всех. Если тест упал, у агента есть два способа его починить, и второй
(поправить ожидание в тесте) всегда дешевле. Поэтому: при падении теста агент либо чинит код, либо
приходит с обоснованием, почему неверна **спецификация** — и тогда таблицу решений правлю я.

Технически поддержано через `CODEOWNERS`: `tests/Unit/Bidding/**` и `tests/Unit/Metrics/**` требуют
моего approve.

### R-12

**Агент не расширяет объём задачи.**

Найденная попутно проблема идёт в отчёт, а не в диф. «Заодно исправил» — самый частый способ
протащить незамеченное изменение поведения: ревьюер читает 30 строк по задаче и пролистывает
остальные 200.

## 5. Гейты

Ни один AI-диф не попадает в бой, минуя эту последовательность. Гейты выстроены по принципу
**«дешёвые и автоматические — раньше, дорогие и человеческие — позже»**, и каждый следующий ловит
принципиально другой класс ошибок, а не то же самое подробнее.

| Гейт | Что ловит | Кто | Блокирующий | Статус |
|---|---|---|---|---|
| **G0** Локально | синтаксис, падение тестов, запрещённые паттерны | авто | да | [есть](../scripts/gates.sh) |
| **G1** Статический анализ | типы, недостижимый код, нарушение границ слоёв | авто | да | план |
| **G2** Юнит-тесты по таблицам решений | ошибки в ветвлениях стратегии и гардов | авто | да | есть |
| **G3** Контрактные тесты API | придуманные пути, неверные единицы, поломанный разбор ответа | авто | да | план |
| **G4** Property-тесты инвариантов | нарушение границ на входах, которых нет в примерах | авто | да | план |
| **G5** Ревью человеком по чеклисту | экономические ошибки, лишний объём, «документация врёт» | человек | да | есть |
| **G6** dry-run / shadow на живых данных | расхождение модели с реальностью WB | человек | да | есть (dry-run) |
| **G7** Канареечный запуск | всё, что не воспроизводится вне боя | авто + человек | да | план |
| **G8** Прод-мониторинг | деградация во времени | авто | — | план |

### G0 — Локальные проверки

```bash
scripts/gates.sh
```

Помимо тестов и `composer validate` — grep-гейты на запрещённые паттерны, потому что они ловят
класс ошибок, до которого статический анализ не дотягивается:

| Паттерн | Почему запрещён |
|---|---|
| `float` / `(float)` в `src/Bidding`, `src/Metrics`, `src/WbApi` | правило R-1 |
| `HttpClientInterface` вне `src/WbApi` | правило R-2 |
| `EntityManagerInterface` в `src/Bidding/Strategy`, `Guard`, `Merge`, `src/Metrics` | правило R-2 |
| `new \DateTimeImmutable()` в `src/Bidding/Guard`, `src/Bidding/Strategy` | правило R-2 |
| `WB_API_MOCK=0` / `WB_API_MOCK: "0"` в файлах, кроме `*.example.*` | правило R-7 |
| `dd(`, `dump(`, `var_dump(` | отладочный мусор |
| Числовые литералы `98765`, `100001` вне `tests/` | демо-данные в прод-коде, [KI-03](KNOWN-ISSUES.md#ki-03) |

### G1 — Статический анализ

PHPStan level 8 + архитектурные правила (Deptrac): запрет зависимости `Bidding → WbApi`,
`Bidding → Doctrine`, `Metrics → WbApi`. Правила R-2 из «договорённости» превращаются в
проверяемое ограничение — иначе они действуют ровно до первого спешного PR.

### G2 — Таблицы решений

Требование: **каждый код причины (`reason`) в стратегии и каждый код блокировки в гардах имеет
минимум один тест**. Это измеримый критерий, в отличие от процента покрытия строк: он гарантирует,
что покрыты именно ветвления бизнес-логики.

### G3 — Контрактные тесты

Ключевой гейт для AI-кода, потому что ловит то, чего агент не может знать, а не то, в чём он мог
ошибиться.

```php
// Смысл теста — не «работает ли», а «в каких единицах и по какому пути»
public function testSetClusterBidSendsDocumentedPayload(): void
{
    $client = new MockHttpClient(function (string $method, string $url, array $options) {
        self::assertSame('POST', $method);
        self::assertSame('https://advert-api.wildberries.ru/adv/v0/normquery/bids', $url);
        $body = json_decode($options['body'], true);
        // Единица зафиксирована в тесте и сверена со спецификацией вручную:
        self::assertSame(150, $body['bids'][0]['bid']); // 15000 копеек = 150 рублей
        return new MockResponse('{"status":"ok"}');
    });
    // ...
}
```

Плюс snapshot-тест: сохранённый пример ответа WB → маппер → ожидаемые DTO. Когда WB меняет схему,
падает snapshot-тест, а не боевой биддинг.

### G4 — Инварианты

Проверяются перебором/генерацией, а не примерами. Список — из [§9 ТЗ](01-TECHNICAL-SPEC.md#9-алгоритм-принятия-решения):

```
для любых (текущая ставка, метрики, пороги, режим):
  new_bid ∈ [min_bid, max_bid]
  final = HOLD           ⟹ new_bid = old_bid
  mode = DEFENSIVE       ⟹ final ≠ UP
  |Δbid| / old_bid       ≤ max_change_pct(режим, направление)
  dry_run = true         ⟹ 0 записей в WB и 0 изменений вне bid_decisions
  status = applied       ⟹ было подтверждённое внешнее изменение
```

Последние два инварианта — прямое следствие найденных дефектов
[KI-08](KNOWN-ISSUES.md#ki-08) и [KI-04](KNOWN-ISSUES.md#ki-04): оба относятся к классу «код делает
ровно то, что написано», поэтому обычные тесты их не видят, а инвариант — видит.

### G5 — Ревью человеком

Обязателен для четырёх зон (`CODEOWNERS`): `src/Bidding/**`, `src/WbApi/**`, `migrations/**`,
`config/**`. Чеклист и разбор того, что именно я на нём отклоняю — [03-AI-REVIEW.md](03-AI-REVIEW.md).

### G6 — dry-run и shadow

- **dry-run** на реальном аккаунте: реальные данные, ноль изменений. Смотрю распределение решений.
  Если 80% решений — `UP`, дело не в удачных кластерах, а в неверных порогах или сдвинутом окне метрик.
- **shadow**: стратегия считает решения непрерывно 24–72 часа, ничего не применяя; сравниваю с тем,
  что сделал бы оператор руками.

Именно здесь всплывают ошибки, которых нет ни в одном тесте: mock отвечает успехом на всё, а живой
WB — 429, пустыми массивами и полями, которых нет в фикстуре.

### G7 — Канареечный запуск

| Шаг | Объём | Длительность | Условие перехода |
|---|---|---|---|
| 1 | 1 кластер, 1 кампания | 1 день | ставка в кабинете WB совпадает с расчётной **до копейки** |
| 2 | 1 кампания целиком | 3 дня | нет решений вне ожидаемых, расход в пределах прогноза |
| 3 | 5 кампаний ≈ 5% расхода | 1 неделя | ROAS не хуже контрольной группы |
| 4 | все | — | — |

Автостоп при: росте расхода более чем на 30% относительно медианы за час; падении ROAS более чем на
20% против контроля; доле `UP` выше 70%; доле `failed` выше 1%.

Шаг 1 существует ровно для одного: сверить единицы измерения ставки глазами в кабинете. Это
единственный способ закрыть [KI-01](KNOWN-ISSUES.md#ki-01) окончательно.

### G8 — Прод

Мониторинг и алерты из [§12 ТЗ](01-TECHNICAL-SPEC.md#12-наблюдаемость), включая алерт «система
ничего не делает». Kill switch — доступен оператору без разработчика.

## 6. Definition of Done для AI-задачи

- [ ] Диф не выходит за перечисленные в задаче файлы.
- [ ] Каждая строка таблицы решений — отдельный тест-кейс.
- [ ] `scripts/gates.sh` проходит.
- [ ] Новых зависимостей нет (или они согласованы отдельно).
- [ ] Значения по умолчанию в сущностях не изменены.
- [ ] Каждое утверждение о внешнем API имеет ссылку на спецификацию.
- [ ] Документация соответствует поведению **после** изменения.
- [ ] Найденные попутно проблемы — в отчёте, а не в дифе.

## 7. Метрики самого процесса

Дефект, пойманный на G1, стоит минуты. Тот же дефект, пойманный на G7, стоит дня и денег селлера.
Поэтому веду учёт не «сколько дефектов внёс AI», а **на каком гейте они ловятся** — это подсказывает,
куда добавлять автоматику.

По этому проекту распределение получилось таким:

| Гейт | Пойманных дефектов | Вывод |
|---|---|---|
| G0–G2 (авто, есть) | мелочи: типы, форматирование | работает, но ловит дешёвое |
| G3 (контракт, **нет**) | 2 критических: [KI-01](KNOWN-ISSUES.md#ki-01), [KI-02](KNOWN-ISSUES.md#ki-02) | отсутствие этого гейта — главный пробел процесса |
| G4 (инварианты, **нет**) | 3 высоких: [KI-08](KNOWN-ISSUES.md#ki-08), [KI-04](KNOWN-ISSUES.md#ki-04), [KI-22](KNOWN-ISSUES.md#ki-22) | второй по важности пробел |
| G5 (ревью, есть) | 8 дефектов, включая архитектурный [KI-06](KNOWN-ISSUES.md#ki-06) | работает, но не масштабируется на объём AI-кода |
| G6 (dry-run на живых данных) | [KI-03](KNOWN-ISSUES.md#ki-03), [KI-10](KNOWN-ISSUES.md#ki-10) — оба невидимы на моках | обязателен, никакой mock его не заменяет |

Главный вывод: **AI-код сдвигает профиль дефектов от логических к контрактным**. Ветвления агент
пишет аккуратно (лучше среднего человека), а вот факты о внешнем мире — придумывает. Значит,
инвестировать надо в контрактные тесты и снапшоты схем, а не в наращивание процента покрытия.

## 8. Чего я себе не позволяю

| Антипаттерн | Чем кончается |
|---|---|
| «Сделай биддер для Wildberries» одной задачей | Правдоподобная система, в которой каждая деталь требует проверки, а проверять уже нечем: нет спецификации, с которой сверять |
| Дать агенту чинить упавший тест без ограничений | Тест подгоняется под код. Спецификация тихо исчезает (правило [R-11](#r-11)) |
| Принять код с новым эндпоинтом «по памяти модели» | 404 в бою либо, хуже, успешный запрос с неверной семантикой |
| Считать зелёный CI разрешением на бой | В mock-режиме опасный путь не исполняется вовсе ([KI-13](KNOWN-ISSUES.md#ki-13)) |
| Позволить «заодно отрефакторить» | Диф разрастается, ревью деградирует до пролистывания |
| Дать агенту прод-креды или боевой токен | Необратимо по определению |
| Поручить агенту выбрать пороги стратегии | Получаю красивые круглые числа с убедительным обоснованием и без связи с маржинальностью |
| Просить агента «проверить свою работу» | Он подтвердит. Проверка должна быть внешней: другой процесс, другие данные, другой критерий |
