# Спецификация алгоритма назначения ставок

Этот документ **первичен по отношению к коду**: при расхождении исправляется код, а не документ.
Каждая таблица здесь — источник тест-кейсов (правило R-4, см. [02-AI-WORKFLOW.md](02-AI-WORKFLOW.md)).

Экономическое обоснование порогов — [§3 технического задания](01-TECHNICAL-SPEC.md#3-экономическая-модель).

## 1. Единицы измерения

| Величина | Тип | Единица |
|---|---|---|
| Ставка (`current_bid_kopecks`, `min/max_bid_kopecks`) | `int` | копейки |
| Расход, выручка | `string` / `DECIMAL(14,2)` | рубли |
| `target_cpa`, `cpa_buffer`, `pause_if_cpa_above` | `string` / `DECIMAL(12,2)` | рубли |
| ROAS, `target_roas` | `string` / `DECIMAL(10,4)` | отношение |
| Проценты изменения | `int` | % |

Все сравнения сумм — через `App\Math\Bc::comp()` с масштабом 4 для отношений и 2 для сумм.

## 2. Параметры кампании

Настраиваются на каждую кампанию отдельно (глобальные значения были бы бессмысленны: пороги
выводятся из маржинальности конкретного товара).

| Параметр | По умолчанию | Смысл |
|---|---|---|
| `metrics_window_days` | 7 | Окно агрегации статистики |
| `level1_enabled` | true | Учитывать ROAS кампании |
| `target_roas` | 4.0000 | Целевой ROAS (справочный, в решениях не участвует) |
| `restrict_up_if_roas_below` | 3.0000 | Ниже — режим DEFENSIVE |
| `allow_up_if_roas_above` | 5.0000 | Выше — режим GROWTH |
| `level2_enabled` | true | Управлять ставками кластеров |
| `target_cpa` | 200.00 ₽ | Целевая стоимость заказа |
| `cpa_buffer` | 20.00 ₽ | Двусторонняя мёртвая зона: HOLD при `target ± buffer` |
| `pause_if_cpa_above` | 400.00 ₽ | Порог паузы (может быть `null`) |
| `min_orders` | 3 | Минимум заказов для решения |
| `min_impressions` | 100 | Минимум показов для решения |
| `min_bid_kopecks` | 5000 (50 ₽) | Нижняя граница ставки |
| `max_bid_kopecks` | 50000 (500 ₽) | Верхняя граница ставки |
| `max_change_up_pct` | 10 | Шаг вверх в BALANCED |
| `growth_max_change_up_pct` | 15 | Шаг вверх в GROWTH |
| `max_change_down_pct` | 15 | Шаг вниз (во всех режимах) |
| `min_change_pct` | 3 | Мёртвая зона по величине шага ставки (гард) |
| `attribution_lag_days` | 1 | Исключить последние N дней из окна метрик |
| `cooldown_hours` | 6 | Пауза между изменениями одного кластера |
| `bidding_enabled` | false | Автобиддинг включён |
| `dry_run` | false | Считать, но не применять |

Шаг вниз по умолчанию больше шага вверх (15% против 10%) — намеренно: выход из убыточной ситуации
должен быть быстрее входа в неё.

## 3. Предусловия запуска

Решения не принимаются вовсе, если `bidding_enabled = false` или `active = false`.
Уровень 2 пропускается при `level2_enabled = false`. При `level1_enabled = false` режим
принудительно `BALANCED`.

## 4. Уровень 1 — режим кампании по ROAS

```
ROAS = выручка / расход        (по окну метрик, источник: GET /adv/v3/fullstats)
```

| Условие | Режим |
|---|---|
| `расход ≤ 0` (ROAS не определён) | `BALANCED` |
| `ROAS < restrict_up_if_roas_below` | `DEFENSIVE` |
| `ROAS ≥ allow_up_if_roas_above` | `GROWTH` |
| иначе | `BALANCED` |

При нулевом расходе режим `BALANCED`, а не `DEFENSIVE`: отсутствие расхода означает отсутствие
данных, а не убыточность. Ограничение роста в этой ситуации навсегда заперло бы новые кампании
на стартовых ставках.

## 5. Уровень 2 — предложение по ставке кластера

```
CPA = расход / заказы          (по окну метрик, источник: POST /adv/v0/normquery/stats)
```

Проверки выполняются строго в этом порядке; первое совпадение возвращает результат.

| # | Условие | Действие | Код причины |
|---|---|---|---|
| 1 | `показы < min_impressions` | HOLD | `impressions_below_min` |
| 2 | `заказы < min_orders` | HOLD | `orders_below_min` |
| 3 | CPA не определена (`заказы = 0`) | HOLD | `cpa_not_available` |
| 4 | `pause_if_cpa_above` задан **и** `CPA > pause_if_cpa_above` **и** `расход > target_cpa` | PAUSE | `cpa_above_pause_threshold` |
| 5 | `CPA > target_cpa + cpa_buffer` | DOWN | `cpa_above_target` |
| 6 | `CPA < target_cpa − cpa_buffer` | UP | `cpa_below_target` |
| 7 | иначе (`target − buffer ≤ CPA ≤ target + buffer`) | HOLD | `cpa_within_buffer` |

Порядок существенен:

- **Значимость раньше экономики** (шаги 1–3). Кластер с одним заказом и отличной CPA — это
  отсутствие данных, а не хороший кластер. При малых числах распределение CPA сильно скошено, и шум
  чаще выглядит хорошо, чем плохо; повышать ставку на таком сигнале — значит систематически платить
  за случайность.
- **Условие расхода в шаге 4.** Пауза требует не только высокой CPA, но и того, что кластер уже
  потратил больше целевой стоимости одного заказа. Иначе кластер выключался бы после первых же
  нескольких показов без заказа.
- **Двусторонний buffer.** Без нижней границы любое `CPA < target` давало бы UP и раскачивало
  ставки на шуме около цели.

## 6. Слияние с режимом кампании

| Предложение | DEFENSIVE | BALANCED | GROWTH |
|---|---|---|---|
| UP | **HOLD** (`blocked_by_defensive_mode`) | UP | UP |
| DOWN | DOWN | DOWN | DOWN |
| HOLD | HOLD | HOLD | HOLD |
| PAUSE | PAUSE | PAUSE | PAUSE |

При блокировке в решении сохраняются оба значения: `proposal = up` и `final = hold`, плюс
`mode_filter = campaign_roas_low_restrict_up`. Это позволяет позже ответить на вопрос «сколько
роста мы не сделали из-за защитного режима» — без такой записи данные были бы утеряны.

Единственное правило слияния — блокировка роста. `DOWN` и `PAUSE` не блокируются ничем.

## 7. Расчёт новой ставки

```
шаг_вверх   = (режим = GROWTH) ? growth_max_change_up_pct : max_change_up_pct

UP:    новая = intdiv(текущая × (100 + шаг_вверх), 100)
DOWN:  новая = intdiv(текущая × (100 − max_change_down_pct), 100)
HOLD:  новая = текущая
PAUSE: новая = текущая
```

Клампинг к `[min_bid_kopecks, max_bid_kopecks]` выполняется в `MinMaxBidGuard`, не в калькуляторе —
чтобы попадание в границу было видно в журнале решений (`below_min_bid` / `above_max_bid`).

Шаг задаётся процентом, а не рассчитывается из отклонения CPA, потому что связь между ставкой (CPM)
и CPA нелинейна и зависит от CTR и конверсии кластера. Любая «точная» формула здесь была бы
эвристикой, притворяющейся расчётом. Процент от текущей ставки — честная эвристика с предсказуемой
амплитудой.

## 8. Предохранители

Применяются только к действиям `UP` и `DOWN`. Первый сработавший превращает действие в `HOLD` со
своим кодом причины; остальные не проверяются.

| Порядок | Предохранитель | Условие блокировки | Код причины |
|---|---|---|---|
| 1 | `MinMaxBidGuard` | новая ставка `< min_bid_kopecks` | `below_min_bid` |
| 1 | `MinMaxBidGuard` | новая ставка `> max_bid_kopecks` | `above_max_bid` |
| 2 | `DeadBandGuard` | `|новая − текущая| < текущая × min_change_pct / 100` | `below_dead_band` |
| 3 | `CooldownGuard` | `now < last_bid_change_at + cooldown_hours` | `cooldown_active` |

`last_bid_change_at = null` (изменений ещё не было) — cooldown не применяется.

Предохранители могут только ослабить действие. Ни один из них не может изменить направление,
усилить шаг или превратить `HOLD` в действие.

Запланированные предохранители и обоснование — [§10 ТЗ](01-TECHNICAL-SPEC.md#10-предохранители).

## 9. Статус решения

| Условие | Статус |
|---|---|
| Предложение было не `HOLD`, а финальное действие — `HOLD` | `skipped` |
| `dry_run` включён (в кампании или в запуске) | `skipped` |
| Иначе | `pending` → далее `applied` или `failed` при исполнении |

## 10. Формат поля `reason`

```
mode=growth; proposal=up; final=up; campaign_roas=5.2000; cluster_cpa=150.0000; reason=cpa_below_target
```

При блокировке режимом добавляется `mode_filter=...`, при блокировке предохранителем `reason`
содержит его код. Хранятся значения метрик **на момент решения** — иначе разбор инцидента через
неделю невозможен: статистика к тому времени уже другая.

## 11. Сквозные примеры

### Пример 1. Защитный режим блокирует рост

```
Кампания:  расход 10 000 ₽, выручка 25 000 ₽ → ROAS = 2.5 < 3.0 → DEFENSIVE
Кластер:   показы 5 000, заказы 10, расход 1 500 ₽ → CPA = 150 ₽ < target 200 ₽
Уровень 2: UP (cpa_below_target)
Слияние:   DEFENSIVE + UP → HOLD (blocked_by_defensive_mode)
Ставка:    без изменений
Статус:    skipped
```

Кластер выглядит прибыльным, но кампания в целом убыточна. Расширяться, не понимая причины
расхождения, — способ ускорить потерю денег.

### Пример 2. Рост в режиме GROWTH

```
Кампания:  расход 10 000 ₽, выручка 55 000 ₽ → ROAS = 5.5 ≥ 5.0 → GROWTH
Кластер:   показы 8 000, заказы 20, расход 3 000 ₽ → CPA = 150 ₽ < 200 ₽
Уровень 2: UP (cpa_below_target)
Ставка:    10 000 копеек × 1.15 = 11 500 копеек (шаг GROWTH — 15%)
Гарды:     11 500 ∈ [5 000, 50 000]; последнее изменение 8 ч назад > cooldown 6 ч → пропущено
Статус:    pending → applied
```

### Пример 3. Снижение и упор в нижнюю границу

```
Кампания:  ROAS = 4.2 → BALANCED
Кластер:   показы 12 000, заказы 5, расход 1 400 ₽ → CPA = 280 ₽ > 200 + 20
Уровень 2: DOWN (cpa_above_target)
Ставка:    5 500 × 0.85 = 4 675 → клампинг до min_bid_kopecks = 5 000
Гарды:     MinMaxBidGuard → `below_min_bid`, final = HOLD, ставка без изменения
Статус:    skipped (proposal DOWN, final HOLD)
```

**Ожидаемое поведение:** ставка упирается в нижнюю границу, и это фиксируется кодом `below_min_bid`.
Кластер здесь убыточен, а снижать ставку уже некуда — регулярные срабатывания на этой границе
означают, что либо `min_bid_kopecks` завышен, либо кластер надо выключать.

## 12. Краевые случаи

| Ситуация | Поведение |
|---|---|
| Расход кампании = 0 | ROAS не определён → `BALANCED` |
| Заказов у кластера = 0 | CPA не определена → `HOLD` (`cpa_not_available`) |
| Текущая ставка = 0 (новый кластер) | Изменение в процентах даёт 0, клампинг поднимает до `min_bid_kopecks` |
| `pause_if_cpa_above = null` | Пауза не применяется никогда |
| Кластер приостановлен | Пока CPA всё ещё выше порога паузы — пропуск; иначе resume (повторная установка ставки, `paused = false`) |
| Данные за окно отсутствуют | Все метрики нулевые → `HOLD` по недостатку данных |
